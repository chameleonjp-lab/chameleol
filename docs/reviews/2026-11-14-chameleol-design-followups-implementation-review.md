#### 3.1 結果カードと共有（T7）

**P01（重要）共有機能が無い端末で、同じタップに本文だけのXを開く【未決B】**
- 根拠（事実）：構造メモ §4.5 は、`navigator.share` が無い時に、主ボタンのタップで本文とURLだけのX画面を開き、同時に案内を出す。要件 EXT-04 は「非対応・画像生成失敗も同じ代替導線を出し、画像を落として文章だけを黙って共有しない」と書き、代替導線は「別タップ」である。見た目メモ §4.5 の表も「非対応では本文だけの共有はしない」。
- 影響：Xの画面が前に開くので、案内は後ろの画面に出る。投稿する時には読めない。要件と見た目メモに合わない。
- 判定：共有機能が無い時も「非対応」と同じにする。主ボタンではXを開かず、案内を出す。「画像を保存」「本文でXを開く」の小ボタンは最初から出しておく。
- 既存試験：`tests/e2e/i18n.e2e.mjs:150` の押す先を「本文でXを開く」へ変える（根拠は EXT-04・RES-08。本文の中身を調べる検査は変えない）。「主ボタンを押しても `window.open` が0回で、案内と小ボタンが見える」試験を足す。ホームの共有（:100-120）は変えない。
- 修正先：構造メモ §4.5 と §8 の R1、T7。

**P02（重要）正式URLが空の時、「null」というURLを渡してしまう**
- 根拠（事実）：`runtime.publicUrl` は meta が空だと `null`（`config/runtime.js:6-8`、`index.html:13`）。構造メモ §4.5 の共有データは `{ files, text, url }`。共有データの `url` は文字列へ変えられるので `null` は "null" になり、「今のページ/null」というURLになる（探査で確認）。既存の `shareToX` は空を除いている（`ui/share.js:26`）。
- 影響：正式URLを入れていない版で、まちがったURLが投稿に入る。
- 判定：`url` が空でない文字列の時だけ項目を入れる。`canShare` 2回と `share` は同じ1つのデータを使う。データの組み方は1つの関数にまとめる（実機でXに画像が付かない時、URLを本文の末尾へ移す切替ができるように）。
- 確かめ方：偽の navigator の単体試験で、URLが null・空・正しい値の3通り。
- 修正先：構造メモ §4.5、T7。

**P03（重要）主人公の準備に失敗したカードを、共有ファイルにしない【未決D】**
- 根拠（事実）：見た目メモ §4.4 は「キャラクター準備失敗」のカードを共有「可（要確認）」とする。本人の依頼は4要素（実色の主人公1体・総スコア・称号・件数）を1枚にまとめることを求める。要件 RES-07 は「準備中・失敗中はX画像共有を成功扱いにしない」。
- 影響：主人公が影絵の、こわれて見える画像が公開の場へ出る。
- 判定：共有ファイルを作らない。画面のカードは影絵と説明を出す。主ボタンを押したら「画像を準備できませんでした」と「画像を作り直す」「本文でXを開く」を出す。「記録なし」（0棟・旧記録・履歴欠損）で、既定の色の主人公を出せた時は共有してよい。
- 確かめ方：描画器を作れない条件で、File が無いこと、主ボタンで共有が呼ばれないこと。
- 修正先：見た目メモ §4.4・§4.5、構造メモ §4.4、T7。

**P04（重要）結果画面の「展開後16MiB」は、今のままでは守れない【未決C】**
- 根拠（事実）：結果アトラスは 2048×2048 で 16,777,216B。上限ちょうど（`tests/e2e/presentation.e2e.mjs:218-236` は画像ファイルだけを数える）。カードの canvas（1200×630）は 3,024,000B。`result-view.js:11-14, 66` は 2048 と各区画の位置を直に書いている。使っている範囲は横1920・縦2040まで。
- 影響：本人の「上限を新旧の合計で満たす」を、いちばん画像が増える結果画面で満たせない。
- 判定（数え方）：その画面で同時に持つ「読み込んだ画像ファイル」「画面につながった canvas」「取っておく主人公画像」の、幅×高さ×4 の合計を 16MiB 以下にする。撮影中だけの描画器は合計に入れず、「同時1個・撮ったらすぐ破棄」で管理する。
- 判定（配分の初期値）：アトラスを 1920×1520 に詰め直す（11,673,600B）。カード 3,024,000B。取っておく主人公画像は切り抜いて 691,200B 以下。開いている1パネルの canvas は 1,254,400B 以下（E090・E075 の倍率に上限を付ける）。合計 16,643,200B。
- 詰め直しの条件：制作スクリプト（`scripts/render-result-atlas.mjs`）で作り直す。背景5枚・立ち姿4枚・視線1枚の画素を、作り直す前と数値で比べて記録する。既存の16MiB試験は変えない。
- 確かめ方：新しい e2e で、パネルなし・E075・E090 の3通りの合計を測る。`result-actions.e2e.mjs` を通す。
- 修正先：見た目メモ §1、構造メモ §4.4・§4.6、T7。

**P05（重要）「画像を保存」が iPhone で写真に保存できない恐れ**
- 根拠：構造メモ §4.4・§4.5 は、画面のカードを canvas にし、保存は download リンクにする（事実）。見た目メモ §9 の案内は「画像を長押しすると写真に保存できます」（事実）。iPhone の Safari では canvas を長押ししても保存は出ない。img なら出る（独立レビュー担当の知識。実機で確かめる）。
- 影響：共有を取り消した後の代わりの道が、主な対象の端末で案内どおりに動かない。
- 判定：「画像を保存」を押したら、準備済みの PNG を img で見せる小さな画面を開く。長押しの案内と download リンクの両方を置く。閉じる時と次の世代で一時URLを解放する。
- 確かめ方：自動試験は img の表示と解放。実機は FOLLOW-03 の手順へ「長押しで写真に保存」を足す。
- 修正先：構造メモ §4.5、見た目メモ §4.5・§9、T7。

**P06（軽微）共有画面から戻っても、連打止めが解けない恐れ**
- 根拠：構造メモ §4.5 は共有の Promise が終わった時だけ連打止めを解く。見た目メモ §4.5 は共有中に小ボタンも無効にする（事実）。Promise が終わらない端末がある（推測。実機で確かめる）。
- 判定：解除を Promise だけに頼らない。画面が再び見えた時・フォーカスが戻った時も解く。小ボタン2つは共有中も無効にしない。
- 修正先：構造メモ §4.5、見た目メモ §4.5、T7。

**P07（軽微）「回して見る」を開いている間、カードの準備が待たされる【未決H】**
- 根拠（事実）：構造メモ §4.6 は、E090 を開いている間に主人公が変わると、閉じるまで主人公画像を作らない。見た目メモ §8.2 は、E090 の主人公はカードと同じ色・段階とする。

- 判定：待たせない。主人公が変わったら、E090 は描画器を一度手放す。カードが先に撮り、E090 は新しい主人公で開き直す。E090 も描き直しが要るので、手放すのは自然。解析中は E090 を「解析中」と出し、描画器を借りない。
- 修正先：構造メモ §4.6、T7。

#### 3.2 輪郭（T1）

**P11（軽微）目の筒の外周の線も、段階で変わる**
- 根拠（事実）：線の材質は、胴・頭・腕・脚・尻尾のほか、目の筒（`chameleon28.js:422`）と舌（:405）にも使う。要件 DES-01 は「外周線」を `K.outline` とシェーダーの色で定義する。目の渦・瞳・内側の輪は画像（:214-230）で別。
- 判定：分けない。同じ材質の線はすべて段階に従う（輪郭が一周そろう）。目の渦・瞳・内側の輪・口・鼻は変わらない。見た目メモ §2.1 の「目…の線は変えない」は「目の画像と口・鼻は変えない」へ直す。本人へ解釈として伝える（5章）。
- 確かめ方：1棟と40棟の画像で、目の渦と内側の輪が同じ濃さであること。

**P12（軽微）本編の描画の倍率は最大2**
- 根拠（事実）：`street.js:84` は `setPixelRatio(Math.min(2, …))`。見た目メモ §2.2 の「3倍で約2物理px」は合わない。見た目メモの計算値（0.63〜0.81 CSS px）なら、段階1の線は描画上 約1.3〜1.6px。
- 判定：線が消えないかの判定は、倍率2の画像で行う（倍率3で撮っても中身は2倍）。細すぎる時に倍率は上げない（処理が重くなる）。値は本人の表のまま、調整判定へ出す。

**P13（軽微）簡易表示の段階8が、今の見た目から変わる**

#### 3.3 舌とダイヤ（T2）

**P14（重要）舌を止める条件が要件より少ない。設定の途中変更も読めない**
- 根拠（事実）：要件 DES-06 の優先順位は「初回ガイド・重大警告・既存の主人公反応→周期の舌」。構造メモ §2.2 の抑止は、ガイド・警察2人・主人公反応の3つで、重大警告が無い。警告が出ているかは app が既に持つ（`app.js:1103-1104` の `activeNotice`）。また `street.js:788` は「動きを減らす」設定を作成時に1回だけ読む。要件は、途中で設定が変わったら収納して取消とする。
- 判定：`presentation` へ `warningActive` を足して抑止に入れる。設定は毎回 `matches` を読む。
- 確かめ方：警告の帯が出ている境界は消費される。途中で設定を「減らす」へ変えると次の描画で収納される。
- 修正先：構造メモ §2.1〜§2.3、T2。

**P15（重要）ダイヤの作りと置く位置が、2つの設計メモで食い違う**
- 根拠（事実）：構造メモ §2.6 は既存の宝石の形と材質を借りる（宝石＋内側の光で2描画、舌と合わせて+4）。位置は舌の先端。見た目メモ §1・§3 は、面ごとに色を持つ専用の1形状（1描画、合わせて+3）。位置は長さの85%の点。保持中に面の色を変える。既存の宝石は単色で、内側の光（半径0.11）は外側（半径0.2）と同じ中心にあり、外から見えない（`chameleon28.js:513-516`）。
- 影響：どちらで作るかで、描画呼出（11か12）、片付けの決まり、見た目が変わる。
- 判定：専用の1形状（頂点の色、不透明）にする。借りても1描画が見えない物に使われ、面の色分けもできないため。舌の所有物として、形と材質を1回だけ破棄する。位置は、舌の同じ計算から「長さの割合の点」と接線を取る関数にする（先端だけにしない）。計画 T2 の「追加2描画」は「追加1描画」へ直す。
