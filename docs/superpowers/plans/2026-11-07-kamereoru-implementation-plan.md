# カメレオる 実装計画書

2026年11月7日 ｜ 対象は `chameleonjp-lab/kamereoru`。マージ済みの[要件仕様書 v1.0](../specs/2026-11-07-kamereoru-design.md)と[受入試験82件](../../acceptance/kamereoru-acceptance.md)を基準にする。チェック欄は後続の実装担当者が証拠を残して埋める。

## 最初に遊べるもの

最初の試作では、iPhoneでパレットを動かし、次の壁に合わせて体色を変え、警戒されずに何棟進めるかを試せるようにする。ここで「同じ色に見えるのに失敗する」「片方の指を離すともう一方も止まる」といった問題を先に見つける。その後、本編の演出・練習・中断再開を組み込み、同じプレイをサーバーでも再現できた段階で順位の登録をつなぐ。

**出発点。** main `a3bed0d` には README・仕様・受入試験・仕様レビューの4ファイルがある。ゲーム、素材、テスト実行環境、データベース変更、公開用の設定はこれから用意する。本計画のパス・関数名・工程の分け方は実装案である。

**採用済みの条件。** 本編は全50棟、通過した棟の平均を使う。20棟目で明るさ操作を導入する。練習は3問。名前は任意で、整理後に同じ名前は1枠に集める。順位は通過棟数、次に小数2桁の平均一致度で決める。30位の同順位者は全員表示する。ほかのゲームの名寄せや件数上限をそのまま使わない。

**技術の分担。** 画面は静的なHTML・CSS・JavaScript、街とキャラクターはThree.jsを第一候補とする。得点・出題を決める小さなJavaScriptモジュールは画面や通信から切り離し、端末とSupabaseの検証処理で同じ版を読む。色の換算、配点、保存周期、通信上限など[仕様第19章](../specs/2026-11-07-kamereoru-design.md)の値は試作値として管理する。

### P1　ゲーム内の時計で、出題と採点を再現する

- [ ] `src/rules/v1/engine.js`、`color.js`、`course.js`、`config.js` と `tests/rules/*.test.mjs` を作る。先に時刻つきの色入力と期待結果を用意する。`makeCourse(seed, generatorVersion)` は50棟の目標色、`advance(state, event, rules)` は次の状態と確定した通過・発見等の出来事を返す。描画速度・音・端末の現在時刻を計算に入れない。
- [ ] 初期設定は1棟5秒。各棟の入口から `[1.5秒, 4.5秒)` を評価し、5秒の出口で1回だけ確定する。前の時刻からの時間を評価開始・終了・通過・警戒100到達の各点で分割する。同じ時刻では直前までの積算→発見の確定→区間・通過の処理→受信順の色変更と進める。猶予にも操作は反映し、警戒と平均はそこで止める。長い処理停止は自動停止へ送る。
- [ ] 色合い・鮮やかさ・明るさの選択値から壁と体の論理色を作る。色の違いを測る候補式（CIEDE2000）と一致度への換算を分け、完全一致が100%、差が広がれば非増加、色差6・14と瞬間状態・平均85%の関係を記録する。換算候補の検算表を先に作り、実機確認まで確定させない。
- [ ] 建物ごとに「一致度×有効時間」を積算して時間で割る。85%の連続成功は丸め前、正確さ点は棟ごとに整数へ四捨五入。順位用の値は通過棟の丸め前の平均をさらに平均し、最後に0.01%単位の整数へ四捨五入する。0棟では平均は空値。警戒は持ち越し、100で発見。仮配点・連続3/5/10の段階・クリア加点は設定から読む。
- [ ] 色の乱数と装飾の乱数を分ける。1〜19棟は明るさ100%で作れる色、20〜22棟は小さな明暗変化、終盤には大きな明暗の交互変化を入れる。同じ番号・版で同じ50色、装飾変更で色順が不変になることを試す。候補生成には試行上限と、その段階の制約を満たす代替色を置く。固定した複数の番号で明暗差・操作距離・似た色の連続数を集計し、実機調整に渡す。

**完了を決める例。** 1秒95%＋2秒75%で建物平均は245/3%。3棟が92・81・87なら86.67%。84.999%はコンボ未達、85.000%は達成。50棟すべて100%なら仮配点で6,080点。249.5秒から250秒未満で途中終了すれば49棟、250秒で50棟。各例を `node --test tests/rules/*.test.mjs` で確かめる。

### P4　練習・一時停止・保存を両立させる

- [ ] `src/practice/session.js` は基本／明るさの各3問を簡単→標準→難しい順に出し、同じ色判定を使う。時間制限は設けず、最初は緑、次問は直前の色・部品位置を保持する。成功の維持時間は約0.5秒を試し、最初の成功時間を固定しつつ最高一致度は問題終了まで更新する。現在値の表示切替、成功後の「次へ」、スキップ時の最後の色と目標色の比較を分ける。
- [ ] 3問を処理した回だけ、両種類合わせて直近2回を残す。全問スキップも完了、途中終了は保存済み履歴に加えない。操作後の終了だけ確認し、答え合わせ・停止中は時間を計らない。本編の回数・自己ベスト・中断位置に触れない。
- [ ] `src/storage/store.js` に端末の複数の値を一緒に書き込める保存機構（IndexedDB）を置く。本編の番号・名義・版・乱数・時計・猶予・色・警戒・評価中の積算・確定済みの棟・得点・コンボ・解放状態・操作履歴の末尾を同じ世代で保存する。通過時、一定間隔、停止時に保存し、周期と失い得る進行幅を実測する。設定・練習・送信待ちは別に保つ。
- [ ] `src/app.js` で画面非表示を停止扱いにし、壁を覆い、音・入力・ゲーム時計を止める。復帰は本人の再開操作とカウントダウン（仮3秒）を経る。途中から新規開始する場合は確認し、旧プレイの確定分を終了待ちへ保存してから次へ進む。破損・未知版は隔離して理由を示す。空き不足で自動整理するのは再取得可能なものだけ。進行中の書込失敗は警告してメモリで続行し、可能なら終了送信する。

**完了の証拠。** `tests/practice/session.test.mjs` と `tests/storage/resume.test.mjs` で、猶予中と通過前後の強制終了、全問スキップ後の次回途中終了、容量不足を再現する。実機では停止中と再開カウント中に壁色が読めず、入力・時計が止まることを確かめる。

### P5　登録名と、通信が途切れても取り違えない開始受付を作る

- [ ] 既存の実験場・サーバーのゲーム識別値、受け付ける項目、閲覧範囲、開始回数の数え方、読み取り先を実装時点で読み取り確認し、`docs/integration-contract.md` に記録する。実験場の[カタログの確認版](https://github.com/chameleonjp-lab/chameleonjp_lab/blob/70bfea7fbf856dbc139f2ef90b2a641db646d693/catalog/games.json)の38件にはカメレオるの項目がない。対象の記録や契約がほかにあるかは未確認。確認前の作業はローカルの代替受付で行い、既存の識別値・他ゲームの表を流用する前に互換性を試す。
- [ ] `src/shared/name.js` を端末・サーバーで共用する。公開説明を開始前に出す。全半角を含む表記の整理（NFKC）、前後の空白除去、連続空白の圧縮後に名前をプレビューする。大小・アクセントは区別する。見た目20文字・内部バイト上限を同じUnicode版で検査し、21文字は切らず訂正を促す。絵文字の結合は残し、改行・危険な方向制御・過大入力は形式エラーにする。名前は文字列として挿入し、文字の方向を行内に閉じ込める。

### P6　終了結果を保全し、サーバーで再現する

- [ ] `src/net/outbox.js` に未送信結果をプレイごとに保存する。発見・途中終了・クリアの確定結果と履歴を端末へ先に書き、演出や画面移動と独立して送る。アプリ切替は終了にしない。サーバーへは終了時にまとめて渡し、分割時は結果番号・順番・総数・内容の指紋を照合して全片がそろってから完全受付にする。
- [ ] 裏で検証する処理 `supabase/functions/_shared/kamereoru/replay.ts` は、開始時に固定した出題番号と当時のルールを読み、初期状態から終了までを再計算する。履歴にはゲーム内時刻・同時刻内の順番・判定に使った色・停止再開・終了理由を入れる。猶予中の色変更も残す。採点用と保存用で同じ値を使い、指の生座標を採集しない。同値圧縮の前後、異なる描画間隔・サーバー実行で結果を比較する。
- [ ] 成立しない51棟や100%超は拒否。高値だけを理由に処分しない。順位値が正しく補助履歴だけが少し違えば正式登録＋内部記録。既知の違いは当時の版で後続の警戒・終了位置まで再計算し、順位値を確定できなければ非公開の確認待ちにする。操作を再現できても、人手による操作を証明したとは扱わない。
- [ ] `supabase/migrations/` に対象ゲームの必要分だけを追加する案を検証環境で試す。公開閲覧・送信元による照会／再審査・サーバーの確定書込・管理者の訂正を分ける。表の直接更新は禁止し、行ごとのアクセス制限と関数の実行権限を両方検査する。秘密はログ・URL・共有文へ出さない。頻度・容量・同時要求を制限し、同じ要求の再送や同名の他人を一律に止めない。
- [ ] 起動・通信回復・手動で再送する。完全受付前は履歴を残し、受付後は状況照会へ切り替える。恒久拒否や別の失敗1件が他の記録を止めないようにする。順位取得だけが失敗した場合は閲覧のみやり直す。開始回数、受理した結果、順位反映のそれぞれに、同じ番号での同時実行・逆順・再実行への試験を置く。

**完了の証拠。** `tests/net/outbox.test.mjs`、`tests/replay/fixtures/`、`supabase/tests/kamereoru_access.sql` を使い、実際の検証用データベースでも分割欠落・同時再送・公開権限での直接更新・別端末の私的記録の照会を試す。保存失敗時も旧未送信の記録を保つ。

### P7　順位と訂正を、同じ計算で表示する

- [ ] 登録済みの1プレイを1行として残す。名前ごとに「通過棟数・2桁一致度」の組が最良の実在プレイを選び、同じ組なら従来の自己ベストを維持する。0棟は回数だけで平均「—」。総得点・時刻を順位に使わない。訂正で首位記録が下がったら過去の正式記録も含めて選び直す。
- [ ] `src/ui/ranking.js` に読み込み中・空・失敗・再試行を作る。サーバーで名前ごとの最良を選んでから、同じ組に同じ順位を振る（1・1・3方式）。順位が30以下の全名に到達できるようにする。ページ内の表示順だけは安定させ、全件が1位でも失わない。ホーム、結果画面で同じ集計元を使い、保留中の新記録に正式順位をつけない。
- [ ] `src/ui/record-status.js` に送信待ち・検証中・確認待ち・拒否・再審査中・正式・訂正を区別して表示する。対象端末の記録を新しい順にたどれ、拒否結果への再審査は1プレイに1回だけ。管理者は必要時にSupabase Dashboardを使う。計算ミスを直せる場合と管理者判断を分け、変更前後・理由・日時を記録して本人のホームに示す。
