# カメレオる 公開後続の実装計画書
**2026年11月18日・反例検証後の実装用確定稿**

この計画の目的は、名前を入力せずに遊んだ人も開始回数に含め、名前付きで正式に登録できた成績から順位と初クリア順を表示できるようにすること。ゲーム内の結果、実験場、Xに渡す本文と画像で、同じ数字を使う。初回に限り、宝石店から1棟目へ逃げる演出を0.7倍速にする。

基準はゲームの main `190e8c4`、実験場の main `70bfea7`。対象の実装先はゲーム [chameleol](https://github.com/chameleonjp-lab/chameleol/tree/190e8c410723935825e3e9206555ee908ae7baf6) と [実験場](https://github.com/chameleonjp-lab/chameleonjp_lab/tree/70bfea7fbf856dbc139f2ef90b2a641db646d693)。作業開始時に両方の最新 main を取得し、以下の関数が移動していたら参照元と既存テストまで追って変更する。成果物は設計と検証結果。以下の実装・配信は後続作業となる。

## 1. 実装の合否を決める仕様

| 利用場面 | 画面・記録・共有が満たす条件 |
|---|---|
| ホーム | 「ランキング」は実験場のカメレオる詳細へ。「Xでシェア」は宝石を盗んだカメレオンが壁色にまぎれて警察から逃げる紹介、ハッシュタグ、正式ゲームURLを渡す。名前入力は任意。 |
| 通常結果 | クリア棟数・ゲームスコア・正式な今回順位を表示。ランキングボタンを設置。「ホームへ」の直下に上位表を置く。共有文に棟数・スコア・今回順位／延べプレイ回数・タグ・URL、画像に発見された棟の壁と同じ色のゲーム内カメレオン・棟数・スコア・今回順位を載せる。 |
| 50棟走破 | 端末で走破が成立した時点で専用結果と専用文・画像に切り替える。50棟、スコア、ゲーム内と同じ虹色のカメレオンを表示。今回の正式順位と登録名単位の初クリア順が確定したら表示・本文・画像へ反映。ランキングボタンと上位表も使える。 |
| 上位表 | 登録名ごとに正式な自己ベスト1件。順位・名前・クリア棟数・平均一致度を表示。見出しを除き最大10行が見え、11行目以降は枠内でスクロール。順位が30位以内の全員を表示し、30位同率で31人以上になる場合も含める。 |
| 本編開始 | 開始時の有効な登録名を固定する。名無しも名前ありも実際に本編が始まったら1回。予約だけ、練習、途中再開、再送は0回。開始後の中断は開始1回に含める。名無しが50棟を走破しても外部への結果送信・順位登録・クリア加算は0件。 |
| 初回の1棟目前 | 宝石店の窓がサイレンのように点滅し、宝石の奪取、逃走、1棟目のガイド開始までキャラとカメラの位置が連続する。初回本編のこの区間だけ表示時間4.0秒。 |
| 実験場 | 一覧から詳細を開けて、詳細から正式なゲームへ戻れる。実験場の開始回数・上位表はゲームと同じ本番の集計元を参照する。 |

**変更範囲の境界**　練習と既存の言語設定は回帰確認のみ。練習の選択肢は①静止してパレット・ガイド付き、②移動してパレット・ガイドなし、③静止してパレット＋明るさバー・ガイド付きの3種類。ホーム左上の言語ボタン、保存した選択を優先する動作、端末言語を特定できない場合のボタン名 `language` と日本語表示を確認する。

**実装に使う集計上の仮定は2つ。** ユーザー指定で確定しているのは、分母が名無しも含む総プレイ回数で、クリア対象が正式にランキング登録された走破のみであること。従来案のうち、次の2点は今回の実装基準として明記する。

| 項目 | 採用する計算方法 |
|---|---|
| 今回順位の比較相手 | 名前付きで正式登録された全プレイ。今回より上の成績の**プレイ件数**＋1。同じ人の過去プレイも比較に入る。総プレイ回数は名無しとリタイアも含むため、画面には「今回のプレイ順位　3位／128人中（延べ128プレイ）」と表示する。 |
| 「何人目」の単位 | 正規化済みの登録名ごとの初回。正式な走破のうち各登録名の最初の1件に順番を付ける。同名の2回目は人数を増やさず「初クリア時の順番：7人目」と出す。匿名の端末記録から人物の同一性を推定しない。 |

## 2. 数字と通信の契約

**識別子とリンク。** 実験場の公開識別子は `chameleol`、既存の判定版・データベース・通信関数の接頭辞は `kamereoru`。既存の保存キーや成績を改名しない。ゲームの正式URLは <https://chameleonjp-lab.github.io/chameleol/>。ホーム・全結果の「ランキング」の行先は <https://chameleonjp-lab.github.io/chameleonjp_lab/ranking.html?game=chameleol>。投稿へ渡すのは前者。

| 概念 | 実装で読む値・返す値 |
|---|---|
| 延べプレイ回数 `totalPlays` | 本番の実開始台帳 `private.kamereoru_launches` の件数。開始1回につき同じ `launchId`。名前ありは予約済み `playId` と結び付け、終了時に加算しない。人数表示用の実人数推定・予約数・ベスト表の人数は使わない。 |
| 順位の比較 | 両方の順位とも `buildings DESC, rank_avg DESC`。一致度は0～10000の整数のまま比較し、表示時だけ百分率の小数2桁にする。スコアや登録時刻を同順位の決着に使わない。並び内の表示順には既存の安定した順序を使う。 |
| 本人の今回順位 `runRank` | 正式な名前付き成績の比較。SQLは対象群のうち `(buildings, rank_avg) > (今回の棟数, 今回の一致度)` の件数＋1。資格のある全プレイ集合で比較してから本人の1件を返す。自己ベストを返す既存の `POST rank` と称号を返す `rankForPassed` は別用途。 |
| 初クリア順 `clearOrdinal` | 今回自身が正式登録済み・50棟・終了理由 `cleared` の時だけ、登録名ごとの順番を返す。30位圏外も対象。途中終了、49棟、無名、審査中、登録不成立には数値を返さない。 |
| スコア | ローカル結果は `summary.score.total`、照合済み訂正があれば同一のプレイ・判定版に対する `verifiedScore.score.total`。棟数・一致度の訂正はその回の正式値を表示する。生データや自己ベストの保存値を画面の都合で書き換えない。 |
| 公開する読み取り | 既存 `GET ranking` は `version, rows[{position,rank,name,buildings,average}], nextAfter, nameCount, restarted` を維持する。新設 `GET stats` は `{ok:true,totalPlays,clearerCount}`。個々の開始・終了履歴、識別子、受付確認用の秘密は公開しない。 |
| 本人だけの読み取り | 秘密を照合する既存 `POST status` の既存項目を保ち、各対象の応答に `metrics:{runRank,totalPlays,clearOrdinal}` を追加する。3値は同じ読み取り時点で取得し、未確定値は `null`。例 `{"runRank":3,"totalPlays":128,"clearOrdinal":null}`。他人のプレイ・無効な秘密には既存の拒否応答を使う。古いサーバーの項目欠落も未確定扱い。匿名の結果画面でも公開上位表は閲覧できる。匿名の本人結果をサーバーに問い合わせる必要はない。 |

| 名前・成績の状態 | 開始件数 | 終了記録と表示 |
|---|---:|---|
| 名無し／明示的に登録せず開始 | +1 | 開始通知だけ。終了送信・結果照会なし。棟数と点は端末で表示・共有でき、「順位登録なし」。走破なら虹色。 |
| 名前あり・途中離脱 | +1 | ブラウザーを閉じ終了結果がなければ開始のみ。ゲーム内の「途中終了」は既存の終了経路で今回の成績を送る。 |
| 名前あり・確認待ち／再送待ち／審査中 | +1 | 同じ終了を再送可。未確定の数値は省略して「集計中」。再送可能な通信失敗には再試行を表示。却下や順位対象外を永続的に「集計中」にしない。 |
| 名前あり・0棟で照合完了 | +1 | 今回のスコアは記録する。`no_rank` として順位と初クリア順は空。 |
| 名前あり・正式登録 | +1 | 今回のスコア・順位を表示。正式な50棟走破だけクリア集計に入り、同名再走破は人数を増やさない。 |

## 3. Codexが実行する順序

各工程は先に記載の反例をテストに加え、旧状態で失敗することを確認してから実装し、そのテストと既存の関連テストを通す。T1～T3の通信契約が決まれば、T4～T6の表示とT7の実験場側を別々に進められる。結合はT8で行う。

### T1　本編開始を1回だけ数え、送信先の混入を防ぐ

**変更先**　ゲーム `src/app.js` の `startFlow / rankedStart / switchToUnranked / beginPlay / resumeSaved / persistEnd / flushNetwork`、`src/net/start.js` の `recordLaunch / flushLaunches`、`src/net/outbox.js`、`src/config/runtime.js`。開始予定、実開始、終了の各保存物を追う。

1. 予約時に作った識別子を引き継ぎ、実際に本編を開始する経路で一度だけ開始記録を永続化する。予約キャンセル・練習・再開からは新規開始を発行しない。初回演出の完了やスキップで2件目を作らない。名前の正規化と有効性検査は既存処理を共有し、開始後の名前変更で登録区分を変えない。
2. 新規の開始・予約・終了の再送データに作成時の送信環境とプロジェクトを保存する。同じ接続先のものだけ再送。単体公開版・試験用記録を本番に流さない。旧データは保持し、旧名前付き記録は元の接続先を既存設定や本人照会で確認できた場合だけ再送。出所を証明できない旧名無し記録は保留する。
3. 名前付きは開始→終了の順に再送する。開始送信後に応答だけ失われても、再送時は同じ識別子。サーバー側も新契約の終了確定前に対応する実開始を照合し、未到着なら既存のデータベースエラー `KM425` に `launch_not_received` を対応させ、応答はHTTP 409、本文を `{ok:false,error:"launch_not_received",retryable:true}` とする。現行の再送処理が本文の指定を受け取り、保留項目を削除しないことを試す。端末が終了・受付確認用の秘密を保持したまま再試行できるようにする。名無しの終了経路からは結果・名前・走破情報を一切送らない。
4. 新契約の適用対象は新しい開始予約にサーバーで印を付ける。新端末が第4版対応を提示した予約に適用し、旧端末の予約および過去の未完了分は従来の手順で受付を続ける。既に確定済みの旧成績は保持し、台帳との不一致は切替前に件数と原因を調べる。開始時刻・人数を推定で作らず、分母が確証を持てない状態では数値表示の公開を保留する。

**試験**　`tests/net/start.test.mjs`、`tests/net/outbox.test.mjs`、`tests/server/start.test.mjs` に、二重タップ、予約後キャンセル、匿名50棟、同じ開始の再送、名前付き終了が開始より先に届く場合、旧保存再開、試験用→本番への接続切替を追加。通信要求の件数・台帳件数・終了件数の3つを照合する。

### T2　公開版と同じ判定で名前付きプレイを受け付ける

**変更先**　`src/net/start.js`、`src/net/verified-score.js`、`src/net/outbox.js`、`scripts/build.mjs`、`supabase/functions/_shared/kamereoru/{handlers,replay}.ts`。ゲームの `supabase/migrations/` に新しい差分を追加し、過去に適用した移行ファイルは編集しない。

現在の公開版の判定は第4版だが、名前付き開始の候補は第3版・第1版。新端末の候補を順に `kamereoru-rules-v4, kamereoru-rules-v3, kamereoru-rules-v1` とする。入口の配列長検査、サーバーの許可一覧と `kamereoru_start_compatible`、操作履歴の再判定、ボーナス明細の返却・受信側の検査、ビルドが出力する推奨版を一緒に更新する。まずサーバーを新旧両対応にする。旧端末は従来の候補、第1版しか示さない旧要求は従来の扱い。第2版で保存した単体プレイの再開も元の版を使用する。再送や再開ではそのプレイの判定版・コースの種・操作履歴を保持する。

**試験**　`tests/net/bonus-start.test.mjs`、`tests/net/bonus-status.test.mjs`、`tests/server/bonus.test.mjs` と再判定用の固定データを更新。第4版の正しい明細は通り、判定版違い、他人の成績、合計の不一致は通らない。第1・3版の既存試験も通ること。ルール原本は `src/rules/v1/`。必要な場合のみ `npm run sync` で複製を同期し、`node scripts/sync-shared.mjs --check` と `npm run check:engines` を実行する。

### T3　正式成績から今回順位と初クリア順を返す

**変更先**　ゲームの新しいデータベース移行、`handlers.ts`、`src/net/outbox.js` の `refreshRecords / settleAccepted`、`src/app.js` の `pollResultFor`。既存の名前別ベスト更新と `kamereoru_ranking_page` を利用する。

1. 正式な結果と登録名を結ぶ共通条件を定義する。今回順位は正式な名前付きプレイ全件、上位表は既存の名前別ベストを使う。双方とも同点は1位・1位・3位。本人の成績だけに絞ってから順位を計算すると全員1位になるため、2節の比較式でテストする。全件比較用の索引は正式成績の棟数・一致度に合わせ、検証データで実行計画を調べる。
2. クリアの正式受付順を非公開で保存する。新設例 `private.kamereoru_clear_admissions(play_id PRIMARY KEY, confirmed_order BIGINT UNIQUE)`。初めて対象条件に入るとき、共通の管理行をロックして受付番号の採番と挿入を同じ取引で行う。同一プレイ再送時は既存行を使用。確認、審査、訂正の全経路で同じ順序でロックする。別名の同時確定・同名の同時確定を別接続で試す。
3. 対象になる走破だけを残した上で、正規化名ごとの最小受付番号順に1から詰めた順番を求める。取り消し時には、その名前に別の有効な走破があればその最初の回を使い、なければ人数から外す。再承認時はそのプレイの元の受付順を使う。人数と順番は照会時点の確定情報。同名の通常プレイに過去のクリア番号を載せない。
4. 切替時の既存の正式走破は `official_at, play_id` 順に一度だけ補う。既存行に再適用しても増えないことと、以後の新規受付順が既存の末尾から続くことを確認。`kamereoru_finalize / kamereoru_admin_decide / kamereoru_admin_correct` と審査要求経路を通し、正式状態から外れた成績を集計に残さない。訂正で棟数だけ50になった途中終了は走破に含めない。
5. 第2節の `GET stats / POST status` を実装。`handlers.ts` は現状 `ranking` だけGETを許すので、経路登録とHTTPメソッド判定の両方に `stats` を追加する。GETで成功、POSTは不許可、実験場の公開オリジンからも読み取れることを検査する。現行の公開順位表の項目・ページ分割を保ち、本人専用の値は既存の秘密照合の後で返す。既存の `POST rank` は自己ベストの呼び出し元に残す。非公開テーブルの直接読み書きを一般利用者に許可しない。

**試験**　`supabase/tests/kamereoru_{ranking,bonus,access}.sql` と `tests/server/{ranking,results}.test.mjs`。Aが50棟、Bが30棟、Aが7棟で全件正式なら、Aの一覧は1位、Aの7棟は3位。名無し1回を加えるとAの7棟は3位／4人中。二重受付・同時確定・却下→承認→再審査・圏外の正式走破・他人の秘密・0棟を照合する。秘密や個別の送信データは公開ログに出さず、受入結果は試験データの件数で照合する。

### T4　ホーム・通常結果・全クリア結果をつなぐ

**変更先**　`src/app.js` の `showHome / showResult / pollResultFor`、`src/ui/ranking.js`、`src/ui/game.css` と既存の結果表示部品。通信の成否と無関係に3画面で実験場への同じ通常リンクを使えるようにする。

1. 結果画面は「もう一度・ランキング・Xでシェア」の操作群 →「ホームへ」→ 上位表 → 振り返り・画像保存などの順に組む。「ホームへ」と上位表を結果欄の連続する要素にし、既存の `.result-actions` の直後に振り返り欄を差し込む処理 が間に入らないよう挿入先を変更する。画面内に同じ上位表を2つ置かない。
2. `createRankingView` に結果用の表示を追加し、既存の `rankingRow / mergeRankingPage` を使う。見出しをリストの外に置き、名前は既存の文字専用描画で表示する。標準文字サイズでは全行を同じ高さにそろえ、リストの最大高さを行高×10、実際の高さを内容に合わせる。文字拡大時も行が重ならず、枠外でページをスクロールできるようにする。長い名前は列幅の中に収め、完全な名前も読み上げ可能にする。
3. 1ページ目を直ちに表示し、`nextAfter` があれば同じ `version` と続き位置で自動取得する。全件取得のための「もっと見る」操作は不要。`position` で重複を除き、`rank <= 30` の境界同率を全員残す。版が廃止され `restarted` が返ったら先頭から置き換える。同じ続き位置の再返却は中断して再試行表示。途中の失敗は取得済みの行を保ち、続きから再試行する。0件・読み込み中・失敗を区別する。
4. 画面の順位は本人の `metrics` から取る。名前別ベスト欄が必要な箇所にだけ既存の `POST rank` を使う。今回の終了結果、照会対象、画面の世代が一致する場合だけ更新する。通信復帰／再試行／画面を再表示したときに本人の状態を取り直し、確認待ち→正式、正式→審査中の両方で数字を更新する。前回のプレイの遅い応答で別人・次回の画面を書き換えない。

**試験**　一覧人数が0・1・10・11・30・31・32の場合を用意。29人が上位、3人が同率30位の時は32行。10位同率でも10**行**が見える。未接続・2ページ目だけ失敗・総回数が未取得の状態・版切替・別プレイの遅い応答、親画面と枠の双方のスクロールを試す。`tests/ui/app.test.mjs` と `tests/e2e/online.e2e.mjs` に加え、公開ボタンの実際の行先も照合する。

### T5　結果画面・投稿文・画像を1つの結果から作る

**変更先**　`src/app.js` の `finishPlay / showResult / shareHome / shareResultText` と共有ボタンの呼び出し元、`src/ui/{share,share-card}.js`、`src/presentation/result-card-{data,controller,draw,ports,view,text}.js`、`src/presentation/result-portrait.js`、`src/scene/{characters,chameleon28,street}.js`。

### T6　宝石店を出て1棟目に入るまでを初回だけ0.7倍速にする

**変更先**　`src/app.js` の初回開始と `playOpening / replayOpening`、`src/scene/{street,stage,opening}.js`。立体描画と簡易描画が呼ぶ `startShopEscape` に `playbackRate = 1` を追加する。初回本編の呼び出しだけ `0.7` を明示する。

`createVisiblePresentationClock` が返す表示中の経過ミリ秒と前フレームからの秒数を、演出の入口でそれぞれ一度だけ倍率換算する。元の `openingPose` の長さは2,800ms。倍率適用後の経過値で姿勢・カメラ・宝石・窓の明滅・効果音のきっかけ・終了を判定する。音の再生速度やゲーム全体の時計には掛けない。合格値は初回4,000ms、あそびかたからの再生2,800ms。初回の窓・奪取／着地／収納のきっかけは表示開始から640／1,920／3,280ms（実描画は次の1フレームまで許容）。

**試験**　時計を固定して4,000ms直前／直後、通常速度、途中のスキップ、背景5秒後の復帰、簡易描画を検査する。`tests/e2e/guidance.e2e.mjs` で1棟目の直前・直後の連続表示を照合し、演出中のゲーム時間・警戒・スコアの増加が各0であることを確認する。
