## 2. 加点の契約

**BON-01 共通：** ①〜④は「評価した棟を完全に通過したとき」だけ確定する。⑤は50棟目を通過してクリアしたときだけ確定する。未通過棟・練習・ガイド専用練習は加算しない。同じ棟の同じ種類は1回だけ。①は2段階のどちらか一方。

**BON-02 精度：** 一致度は既存の整数単位（1% = 1,000,000）を使う。建物平均の比較は `matchSum >= thresholdUnits * evalMs` とし、表示の丸めを判定へ持ち込まない。95%・98%の手前の値を四捨五入で達成扱いにしない。

| ID | 名称 | 条件 | 加点 | 1プレイの上限 |
|---|---|---|---:|---:|
| B1 | 精密擬態 | 棟平均95%以上98%未満は+5、98%以上は+10 | 5 または 10 | 500 |
| B2 | 安定擬態 | 評価区間内で90%以上が連続2500ms以上 | 5 | 250 |
| B3 | 到達 | 通過棟数が10・20・30・40・50になった時 | 20 | 100 |
| B4 | 素早い色合わせ | 評価開始から500ms以内に始まった95%以上の連続区間が1000ms以上になる | 5 | 250 |
| B5 | 全棟成功 | クリアかつ、全50棟それぞれの丸め前平均が85%以上 | 100 | 100 |

**BON-03 時間：** 評価区間は `[入口+1500, 入口+4500)`。ゲーム内の整数ミリ秒で測り、描画回数・実時間・音楽の時刻を使わない。B2は通算2500msではなく最長連続時間。B4は「達成の完成が500ms以内」ではなく「その連続区間の開始が500ms以内」。500msちょうどの開始は対象、501msは対象外。1000ms維持後に色が外れてもB4の達成はその棟内で保持する。維持前に外れた場合は候補を解除し、500ms以内なら次の候補を認める。

評価開始時点で95%以上ならB4の開始を0msとする。猶予中の色合わせで準備する遊び方を認める。猶予の時間そのものは維持時間へ入れない。停止中は時間を足さず、再開後は停止前の連続区間を継続する。

**BON-04 同時刻入力：** 長さ0msの色はB2/B4の達成にも中断にも数えない。現在の履歴圧縮は同時刻の連続色入力を最後の1件へまとめるため、時間が実際に進んだ区間だけを積算する。入力イベントを受けただけで連続時間をリセットしない。

**BON-05 ガイド：** 初回の本編ガイドも通常本編と同じ判定を使う。静止ガイド中の実時間は数えず、ゲーム時刻を再開してから評価する。ガイド表示済みフラグで加点を分岐させない。正解位置の補助により初回のB1/B2/B4が取りやすくなることは、この計画の補完方針として明記する。総得点は順位に使わず、ガイドや順位の既存方針は変えない。

**BON-06 付与の順：** 既存どおり「直前区間の積算→発見確定→評価終了→棟通過→その時刻の入力」。発見が先に成立したら通過点を付けない。出口と同時刻の手動終了は、エンジンが先に確定した通過を維持する。50棟目では通常点・B1〜B4・クリア200・B5をすべて確定してから、保存・演出へ渡す。

### 点数の検算

全50棟を評価開始から100%で通過した場合、旧来の内訳は通過1000＋正確さ4000＋連続880＋クリア200＝6080。追加は500＋250＋100＋250＋100＝1200、総得点は **7280点**。会話の7230点は「①②③のみ＋クリア500」の別案であり、今回の上限ではない。

10棟目の平均98%、10連続成功、B2/B4も成立する例は、通常20＋78＋20＝118、B1/B2/B3/B4＝10＋5＋20＋5＝40、今回158点。50棟目が100%・50連続・全条件成立なら、その棟の通常120＋B1〜B4の40＋クリア200＋B5の100＝460点。

## 3. 旧記録と難易度を維持する版構成

現コードではランキング開始とサーバー再計算は `kamereoru-rules-v1`、新規の単独プレイは警戒上昇を一部緩和した `kamereoru-rules-v2` を使う。単独用をそのままランキングに流用すると難易度まで変わるため、別々の後継版を作る。

| 版 | 用途 | 今回の扱い |
|---|---|---|
| v1 | 既存ランキング、旧保存・未送信結果 | 定数・結果JSONの形・採点結果を維持 |
| v2 | 既存単独プレイ、旧保存 | 警戒緩和と結果JSONを維持 |
| v3（新規） | ランキング用のボーナス追加版 | v1の色・出題・警戒・時間・順位を継承し、追加点だけ導入 |
| v4（新規） | 単独プレイ用のボーナス追加版 | v2の条件を継承し、v3と同じ追加点を導入 |

識別子は `kamereoru-rules-v3` / `kamereoru-rules-v4`、追加内訳形式は `kamereoru-bonus-v1`。出題版は変更しない。実装着手時に番号が使用済みなら衝突を解消し、この表と関連試験を一緒に更新する。版を名前だけで上げ、既存のv1/v2の意味を書き換えることは禁止する。

### 開始受付と切替

新クライアントは開始要求の作成時に `supportedRulesVersions: ['kamereoru-rules-v3','kamereoru-rules-v1']` を端末へ保存し、再送でもその値を使う。旧要求の欠落値はv1だけとして扱う。応答は送信時の対応一覧に含まれる既知の版・出題版・要求番号・名前・出題番号で検証し、実際に受け付けた版でセッションを作る。

新サーバーはv3とv1のうち、クライアントと受付設定の両方が対応する最新版を、新規の開始だけに選ぶ。旧クライアントはv1、旧サーバーが返すv1も新クライアントは受け付ける。v4はランキング開始には認めない。同じ要求番号が登録済みなら、保存済みの版を返す。応答消失中の更新や同時要求で、別の版・プレイ番号を作らない。

新しい `private.kamereoru_start_compatible(requestId, secretHash, launchId, displayName, nameKey, gameVersion, supportedRulesVersions)` を追加する。既存の8引数関数は残す。新関数は既存行を照会し、未登録なら版を選んでINSERT、競合なら登録済み行を読み直す。どちらも秘密・名前・launchId・gameVersionを照合し、保存済み版が要求の対応一覧内であることを確認して返す。未知の版・重複・空配列・3件以上は拒否する。新関数も非公開の権限を維持する。

## 4. 採点データと表示の責務

**DATA-01：** B2/B4は既存の色・ゲーム時刻の履歴から再現する。ボーナス獲得通知や演出状態を操作履歴へ追加しない。1棟の評価用状態に、90%以上の現在／最長連続時間、95%以上の現在の候補開始・維持時間、速さ達成済みを持つ。終了時にその棟の評価結果へ閉じ、通過時に加点する。

**DATA-02：** v3/v4だけに `score.bonus`（5種の合計）と `summary.bonus` を追加する。旧版の `summary` にゼロの新項目を足さない。`score.total = pass + accuracy + combo + clear + bonus`。`summary.perBuilding` は3要素配列を維持し、第3要素には通常点＋その棟のB1〜B4を入れる。クリア200とB5は棟別配列の外に1回だけ持つ。

`summary.bonus` の契約：`{format, points, totals, awards}`。`totals` は `precision5, precision10, steady, milestone, quick, allSuccess` の6項目で、各 `{count, points}`。表示上は精密2段階を1行にまとめる。`awards` は最大156件、各 `{id, building, kind, tier, points, earnedAtT}`。kindは `precision|steady|milestone|quick|allSuccess`、tierはprecisionのみ5/10、それ以外はnull。idは `${rulesVersion}:${building}:${kind}`、表示側はplayIdと組にして重複を防ぐ。B5はbuilding=50。点数・件数・内訳合計を照合する。

`earnedAtT` は実際に加点を確定する棟の出口時刻（`building * rules.buildingMs`）。条件が評価途中で成立した時刻や、画面が通知を受け取った時刻を使わない。B5も50棟目の出口時刻を使う。

`pass` イベントは既存項目を保ち、v3/v4のみ `basePoints, bonusPoints, bonusAwards` を追加し、`points` は通常点＋B1〜B4とする。B5は終了時のsummaryに存在し、専用の画面用イベントを再採点の根拠にはしない。

**DATA-03 保存：** 途中保存・結果・送信待ちに同じ版の内訳を保つ。復元は元の版で履歴を再計算し、B2/B4の途中状態まで復元する。v1/v2保存は旧結果のまま。採点版が不明な保存は保護して理由を表示する。表示の「見た／見ていない」は再加点に使わない。

**DATA-04 サーバー：** SUPPORTED_RULESにv3を加え、開始記録の版で全ボーナスを再計算する。v4は単独用で、ランキング受付へ追加しない。申告したbonusの過大値を採用しない。ただし順位用の値が一致する補助得点だけの差異は、既存どおり正式登録＋内部記録とし、名前や順位を不必要に保留しない。

v3の再計算済み補助値を `verdict.verifiedScore = {rulesVersion, score, bonus, perBuilding, maxCombo}` に保管する。棟別得点も訂正しないと、総得点だけ正しくて内訳が古い状態になるため、`perBuilding`も含める。本人用の秘密照合がある状態取得で、検証が完了した `official` / `no_rank` にだけ同じ `verifiedScore` を追加し、公開順位には出さない。検証途中・審査中・拒否・旧版などで値が無い場合は省略する。

クライアントはplayId・版、整数値の範囲、種類・重複、件数・点数・内訳の合計を確認し、正常な値だけを `records.verifiedScore` に保存する。表示用summaryでは `score, bonus, perBuilding, maxCombo` をまとめて置換する。元の結果summary・送信body・bodyShaは保持し、再表示でも同じ保存済み訂正値を重ねる。`sum(perBuildingの第3要素) + score.clear + B5点 = score.total` と `score.bonus = bonus.points = 各種類の合計` を満たすこと。同じstatusのまま訂正値が届いた場合も画面を更新するが、補助点だけの訂正を新たな警告・順位保留・獲得演出・再加点の理由にしない。

## 5. 5種類の演出

| ID | 表示と動き | 音・終了後の扱い |
|---|---|---|
| FX1 | 「精密擬態 +5」／「超精密擬態 +10」。カード内の2つの輪が重なり点数が出る。+10は二重の輪と少量の光 | 澄んだ短音。精密の2段階は同時表示しない |
| FX2 | 「安定擬態 +5」。揺れた線が水平になりチェックが付く | 落ち着いた短音 |
| FX3 | 「{n}棟突破！」「到達ボーナス +20」。10/20/30/40/50の今回の印に旗が立つ | 上昇する3音。10棟目に入った瞬間には出さない |
| FX4 | 「素早く擬態！ +5」。カード内を短い矢印が走って止まる | 短い風切り音と1音 |
| FX5 | 「全棟成功！ +100」「全50棟で成功」。宝石を取り出す既存のクリア動作に勲章を重ねる | クリア音と一体の終止音。全棟100%ではないため「パーフェクト」と呼ばない |

**FX-01 通常画面：** 得点欄近くの1枚のカードに「ボーナス」を常に明記。1種類は1行、同時獲得は合計を大きく、4種類までを2列×2行で表示する。表示順は①②④③。種類ごとにカードを積み上げない。最大1枚・光の粒は合計8個・追加の描画ループや3D描画器は作らない。マーカー・壁の比較面・体色・次の壁・警戒ゲージを覆わない。既存のコンボ宝石と区別できる記号を使う。

**FX-02 時間：** 入口通過後の猶予に0〜1400msで表示する。出現150ms、静止1000ms、集約と退場250msを初期値とする。遅いフレームでもイベント時刻からの経過で短縮し、次棟評価開始1500msには残さない。停止中・非表示中は演出時計も止める。ガイド・警告が必要ならカードを同じ場所の静止した文字と点数へ縮小し、音と粒を抑える。通知を後から連続再生しない。

**FX-03 得点：** 通常点（通過＋正確さ＋連続成功）、ボーナス、今回合計を区別する。点数が得点欄へ移動する動きと総得点の小さな1回の拡縮で反映を伝える。採点自体は通過時に済ませ、表示の数え上げから得点を書き換えない。途中で画面を閉じた場合は確定値を採用する。

**FX-04 音：** 既存mixer内へ追加し、別AudioContextを作らない。1棟で獲得音は1回。単独なら種類専用音、複数なら `bonusMulti`。既存の通過音・連続成功音・到達音との同時発音を選択処理でまとめる。優先は発見／クリア→操作ガイド・解放・危険→複数／到達ボーナス→単独ボーナス→通常通過。連続成功の節目は文字で残し、ボーナス音へ一体化する。pass内で即再生せず、同じイベント列のenterBuilding・clearと、その更新処理で後から決まる警告まで集めてから1回選ぶ。mixerの発音数上限だけで競合が解消すると扱わない。重要音のために見送ったボーナス音は後から鳴らさない。全体消音・効果音量0・音声利用不可では文字を残す。

**FX-05 終了：** 50棟目のpass直後にゲーム用表示が破棄される既存処理を考慮する。最終棟の内訳は、確定結果の保存を試みた後、採点済みsummaryから終了画面用表示へ渡す。保存失敗時は既存の警告とメモリ上の結果表示を維持し、保存成功を装わない。最後のB1〜B4、クリア200、B5の100を別項目として示す。B5は既存終了演出の中で1500〜2000msを上限に表示し、見せるためだけの待機を追加しない。終了演出を即スキップしても全点と内訳が結果へ残る。

**FX-06 結果：** 「今回のボーナス合計」と5種類の回数・合計点を追加する。精密は+5の回数と+10の回数を補足する。B5未達は「未獲得」、旧版は「この記録はボーナス導入前」と区別する。旧版の総得点へ0点の新制度を適用したような表示にしない。既存の2つの得点内訳表示（appとresult-view）を同じ表示用データへ統一し、同じ総得点を重複して数え上げない。再表示・言語変更では獲得音を繰り返さない。

**FX-07 端末・翻訳：** iPhone 17 Pro Safariの縦横、402×700／402×874／874×402を対象とする。文字は原則14px以上を初期値にし、収まらない場合は公式な短い翻訳と折返しを使う。小さくする・三点リーダーで種類や点数を消すことで解決しない。ja/en/es/pt-BR/zh-Hans/fr/de/ko/ru/it/zh-Hant/id/tr/vi/thを対象とする。ボーナス名、回数、説明、未獲得、旧版の説明も翻訳する。

動きを減らす設定では移動・拡縮・粒・線の走査を止め、同じ名前と得点を静止表示する。色や音だけで獲得理由を伝えない。表示要素は操作を遮らず、プレイ中の操作部品の位置と大きさを変えない。

## 6. 選んだ実装方式

| 方法 | 評価 |
|---|---|
| 画面側でボーナスを計算して加点 | 保存復元・サーバー検証・描画速度で差が出るため採用しない |
| 終了時に履歴を全部読み直して初めて計算 | 結果には出せるが、棟通過時の確定演出と結びつかないため採用しない |
| 共通判定エンジンで区間ごとに積算し、表示は確定結果を読む | 採用。B2/B4の途中状態を復元でき、同じ履歴をサーバーで再現できる |

追加負荷は入力区間ごとの定数個の整数計算と、1棟につき最大4件の通知データに抑える。性能を確認済みとはしない。音・表示・通信が失敗しても、判定と保存の確定値を取り消さない。
